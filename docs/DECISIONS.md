# sNotate: decisions

Single source of truth for choices that shape the code. Newest at the bottom. Supersede, never rewrite.

## 2026-10-25 Name: sNotate

Why: lower-case s plus a verb, parallel to sView; `snotate` as binary and config directory. Rules out: sNotation, SNotate, sNote (Note reads as text, not image).

## 2026-10-25 Scope: PoC evidence folders only

Why: one user, one workflow (a step-by-step evidence procedure); do one thing at once and do it well. Not for sale, not general purpose. Rules out: backgrounds, device frames, recording, upload, cloud, collaboration features, anything a customer other than Sam would ask for.

## 2026-10-25 Capture is not in v1

Why: the Guide-Shot AppleScripts and the macOS screenshot tool already produce the captures; capture needs the Screen Recording permission and ScreenCaptureKit work that would delay the annotation core. Planned as Phase 6 after `v0.1.0` has produced a real report.

## 2026-10-25 Stack: same as sView

Swift 6.2, SwiftUI shell, AppKit canvas, Apple frameworks only, macOS 26 Tahoe, no third-party packages, Xcode 26, XcodeGen project, Makefile targets. Why: one set of conventions for two sibling apps, one brain. Details in `02-tech-stack.md`.

## 2026-10-25 Config in `~/.config/snotate/`, Linux style, lower-case paths

Same rule as sView: `config`, `keymap`, `styles` hand-edited plain text, `state.json` disposable, whole directory exportable. Nothing in `~/Library/Application Support`.

## 2026-10-25 Annotations in one JSON sidecar per case, originals never written

Why: non-destructive, diffable, re-exportable; one file per case keeps counters continuing across steps simple. Format in `02-tech-stack.md`. Rules out: flattening on save, per-image sidecars, Markdown or YAML for geometry.

## 2026-10-25 Captions live in the memo, not in the sidecar

Why: the memo `<case-id>.md` is already the report draft the evidence procedure produces; sNotate edits its `- description` lines in place rather than inventing a second place for the same text. The sidecar holds a caption only until a memo exists.

## 2026-10-25 Shared code with sView is copied, not shared, until a third sibling exists

Why: about 400 lines (folder scan, natural sort, poc parsing, config, keymap) are cheaper to keep in sync by hand than a cross-repo package is to coordinate for one person. Extract `scommon` at the rule of three. Superseded the same day, see below.

## 2026-10-25 Export location: `<case-folder>/notated/<same-file-name>.png`

Why: `export` says nothing; `notated` says what was done to the files and by which tool. Originals stay where the memo references them; the notated copies carry the same names so a report can point at either folder. Rules out: in-place export with originals moved aside. The directory name is `notated_dir` in `config` and should not be changed per case.

## 2026-10-25 Pixel coordinates are reusable because captures have fixed geometry

Why: captures of one PoC are taken from the same window at the same size, so step N+1 is pixel-identical in dimensions to step N and a blur or crop drawn once applies to every step, and to a re-shot step. Observed in a real PoC tree: captures of the same window at both 1x and 2x. The sidecar therefore records the image pixel size next to the coordinates, and sNotate scales annotations by the ratio when a step's pixel size is an exact multiple of the recorded one, and warns otherwise. Keeping the scale constant at capture time is sCapture's job (`scapture/docs/DECISIONS.md`).

## 2026-10-25 Capture belongs to sCapture, not sNotate

Why: a third sibling, sCapture, owns everything between the screen and the case folder. sNotate's E7 and Phase 6 are withdrawn; sNotate only opens what sCapture (or the AppleScripts, or `screencapture`) wrote.

## 2026-10-25 Branding follows the s-family note

The s means super-fast and swift, never expanded in the product; sNotate's icon is the shared s mark on amber with a step-counter dot as the accent, from SVG layers and an Icon Composer `.icon` in `brand/`. Source of truth: sView's `docs/04-branding.md` until it moves to `scommon/brand/`.

## 2026-10-25 Shared code becomes the `scommon` package

Why: sCapture is the third sibling, so the rule of three is met. `scommon` is an SPM package in its own sibling repository holding folder scan, natural sort, `poc-` case and file-name parsing, the `key value` config parser, the keymap grammar and the config-directory logic; each app depends on it by local path (`../scommon`) and pins nothing, since one person edits all four repos. Timing: extracted when sView Phase 2 is reviewed and the copies have tests; until then sNotate Phase 0 copies as planned.

## 2026-10-26 Phase 0 copies sView's `SCommon` target whole

Supersedes "until then sNotate Phase 0 copies as planned" in the `scommon` entry. Why: sView split its shared code into an `SCommon` target (sView's `docs/DECISIONS.md`, 2026-10-26) because the five files the plan listed would not compile outside sView (`Keymap` parsed into sView's `Command`, `Config` was sView's option list). sNotate therefore copies `Sources/SCommon` and `Tests/SCommonTests` byte for byte as its own `SCommon` target, which `SNotateCore` depends on and re-exports; sNotate's settings use `ConfigPaths(app: "snotate")` and will define their own `KeyValueSettings` type. Changes to the shared code are made in sView first and copied over whole, so the two copies never diverge. The extraction to the sibling `scommon` repository replaces the copy with the package dependency in one commit. Rules out: copying individual files, editing `Sources/SCommon` only here, and sView's `Config` or `Command` in sNotate.

## 2026-10-26 AppKit app lifecycle; SwiftUI only for views

Supersedes the "SwiftUI shell" part of the stack entry, following sView's 2026-10-25 decision. Why: in sView the SwiftUI `WindowGroup` dropped its default window when the app was launched with a path argument, and sNotate opens case folders the same ways (Finder, `open -a`, argv, the `snotate` launcher), wants one case per window and the canvas as first responder. `main.swift` installs an `NSApplicationDelegate`, windows are AppKit, the menu bar is built in code; SwiftUI stays for views that suit it, such as the storyboard grid and the inspector, hosted in `NSHostingView`. Rules out: SwiftUI `App`, `WindowGroup` and `Commands`.

## 2026-10-26 Animated step-by-step guides are a planned output, as a feature or as the sibling sWalk

Why: a notated case is already a scene list (one scene per step, annotations in sidecar order, captions from the memo, fixed geometry so a crossfade shows only the UI change), which is manim's model in a much simpler form; rendering it with time as a parameter gives a training clip without a screen recording. Two placements are open and decided later, after `notated/` export has produced a real report: a `:walk` export inside sNotate (same `Renderer`, `AVAssetWriter`), or a fourth sibling `sWalk` that takes a case folder with its sidecar and memo as input and writes video files, keeping sNotate a notation tool. What is fixed now: the sidecar and memo are the only inputs, so sNotate must not grow a second animation-only data file; any timing or camera hints go into the sidecar under their own keys, preserved by the unknown-key rule. Downstream: the clips are generated programmatically alongside the Typst documents, so a case id names a memo, a notated folder, a Typst page and a clip. Backlog SN-406.

## 2026-10-26 Sidecar bytes come from our own writer, unknown keys kept per object

Why: the sidecar must survive both newer and older sNotate versions and show a one-line diff for one moved arrow. It is parsed into a small `JSONValue` tree (`JSONSerialization` blurs bools and numbers and is not `Sendable`); known keys map into `Sidecar` and `SidecarStep`, every other key stays in `extra` on the root and on each step and is merged back on write, and items stay raw JSON until the model reads them, keeping their own unknown keys. `SidecarWriter` fixes the bytes: keys sorted, two-space indent, `"key": value`, arrays of plain numbers on one line (`"crop": [0, 88, 1920, 992]`), other arrays and objects expanded, numbers rounded to two decimals without trailing zeros, text written as is apart from JSON's required escapes, a trailing newline. Rules out: `JSONEncoder` (writes `"key" : value`, escapes slashes) and dropping keys this version does not know.

## 2026-10-26 Every step records its pixel size; opening a case never writes

`size` is required in the format and written from the image header (ImageIO, no decode). An old sidecar without it opens fine: the size is filled in memory and reaches the disk with the first real change, as do entries for images found since. Why: opening, browsing or exporting must not churn git. The scale rule compares the recorded size with the file: equal, a whole multiple k in either direction with the same k on both sides (annotations scale by k or 1/k), or flagged. Rules out: writing on open, scaling by a non-integer ratio.

## 2026-10-26 Undo: one entry per Command, text edits coalesced, case-wide

One undo entry per dispatched Command; typing in a text field is one entry for as long as the field stays active. The stack covers the whole case (SN-105), is unlimited within the session and is not persisted. Why: undo should match what the author thinks of as one action, and per-keystroke entries make undo useless after a caption. Implemented with `Commands` and the `Dispatcher` later in Phase 1.

## 2026-10-26 An unreadable sidecar makes the case read-only

When `<case-id>.snotate.json` does not parse (git conflict markers, a half-written file, a wrong type), the case still opens from the folder alone, the reason is shown, and nothing is saved until the file parses again, which the folder watch notices. A change still waiting to be saved when the sidecar changes outside is saved first if the file is as sNotate left it, otherwise the outside version wins and the session reports the dropped change. Why: overwriting a conflict destroys the other side's work; a checkout or merge is the likelier truth than the last half second of editing. Rules out: saving over a file sNotate cannot read, and silently merging.

## 2026-10-26 Step files are paths relative to the case folder; `assets/` is scanned

A case's captures are the images directly in the case folder plus those in an `assets/` sub-folder, which some real cases use; the sidecar key is the path relative to the case folder (`assets/scap-...png`), so no other code needs a special case. Other sub-folders, `notated/` among them, are not scanned. The export path for an `assets/` step (`notated/assets/...` or flattened) is decided with the `Exporter`. Rules out: top level only, and scanning the whole tree.

## 2026-10-26 Memo captions: what the locator reads and how an edit writes

The memo is kept as lines with their own endings (LF, CRLF, none at the end) and an optional byte-order mark, so unchanged bytes round-trip exactly; it must be UTF-8, otherwise the case opens without captions and the reason is shown. An image's caption is the first unindented `- `, `* ` or `+ ` line above its `![...](path)` line, past blank lines and indented sub-bullets, which are exposed read-only; references in code fences are ignored; paths are compared with step keys after dropping `./` and decoding `%20` and `<...>`. Choices approved with the plan: when an image is referenced twice, the first reference's bullet is the caption, edits change only that line, and the others are reported; an edit keeps the bullet marker, the trailing whitespace and the line ending of the line it rewrites; a bullet reading exactly `description` is the evidence script's placeholder and shows as an empty caption; a caption is one line, a line break is refused, and sub-bullets stay hand-edited in v1; a caption is written only if the memo file still holds the bytes it was read from, never over an edit made elsewhere. Rules out: a Markdown parser, normalising line endings or whitespace, and rewriting more than the one line (with the exception below).

## 2026-10-26 An image without a bullet gets one inserted

When the author captions a step whose image has no bullet above it, `- caption` and a blank line are inserted above the image line in the file's own line endings, with a blank line before them when the line above is text. Why: it gives the memo the shape the evidence script writes and keeps the caption in the memo rather than in the sidecar. This is the one exception to "the memo is edited one bullet line at a time" (CLAUDE.md). Rules out: refusing the caption, and moving or rewriting the image line.

## 2026-10-26 The memo is read with the case; caption editing in the session waits for Phase 3

`CaseDocument` reads the memo when the case opens and `CaseSession` watches the memo file as well as the folder, so editors that save in place are seen. Setting a caption through the session, the sidecar caption fallback while no memo exists, and the migration when one appears come together in Phase 3 with the storyboard, as the plan has it.

## 2026-10-26 Annotation item format

Supersedes the item shapes in the `02-tech-stack.md` example, which now shows this format. Every item is an object with `type` (`arrow`, `rectangle`, `ellipse`, `counter`, `text`, `highlight`, `blur`), its geometry in stored image pixels (`from`, `to`, `at` as `[x, y]`; `rect` as `[x, y, width, height]`, normalised on read) and `preset`, always written. Variants are written only when set: `curve` on an arrow, `fill` on a rectangle or ellipse, `pill` and `leader` on text, `spotlight` on a highlight, `pixelate` on a blur; `at` on text is its top-left corner. A step's `crop` is a typed rectangle and `restart_counter: true` starts its counters again. Why: one key per fact, nothing written that a default already says, so adding a tool option never rewrites existing sidecars. Rules out: storing style values per item (the preset carries them until a per-item override is needed).

## 2026-10-26 Counter numbers are derived, not stored

A counter's number follows from story order: counters continue across steps when the root `counter` is `continue` and start at 1 per step when it is `step`, and a step with `restart_counter: true` starts again. Why: SN-203 renumbers on every insert or delete, and a stored `n` would rewrite every later counter in the sidecar for one change. An `n` key in an older file is kept as an unknown key and ignored. The numbering itself is built with the Renderer.

## 2026-10-26 Annotation ids live in memory only

Each annotation gets a UUID when the sidecar is read; it is never written and does not take part in equality, so the sidecar holds no random strings and a reload of identical content compares equal. Commands refer to an annotation by step file and id. A reload with different content assigns new ids, which clears the selection. Rules out: persisted ids, and identity by array index (z-order changes would break it).

## 2026-10-26 Unreadable items are kept, not fatal

An item of a type this version does not know (from a newer sNotate) or a known type it cannot read (an arrow without `to`, a `pill` that is not a bool) becomes `.unknown` with the reason: written back byte for byte, never drawn or hit, and listed in `Sidecar.itemIssues` for the UI. Only a sidecar that is not JSON, or whose root, step or crop has the wrong shape, makes the case read-only. Why: one bad item should not lock a case, and dropping it would lose someone's work.

## 2026-10-26 Stored coordinates stay at the recorded size

Annotations are stored in the pixels of the step's recorded `size`. On a step that is an exact multiple the canvas and renderer scale them with `StepTransform` and edits go back through `toStored`, so a 2x re-shoot never rewrites the sidecar; on a flagged step they are used unscaled and stay editable. A command to re-record a step's size after a re-shoot is a later item. Rules out: rewriting coordinates when the image changes.

## 2026-10-26 The core may import CoreText and CoreImage

Supersedes "Foundation, CoreGraphics and ImageIO only" for the core. Why: text bounds must match drawn text, and the single renderer for screen and export (Core Text for text, Core Image for blur and pixelate) is core code. Still never AppKit or SwiftUI, so `swift test` stays headless. CLAUDE.md and the tech stack say so.

## 2026-10-26 Geometry types and selection rules

Points and rectangles are `CGPoint` and `CGRect` in stored image pixels, origin top-left, y down; rounding to two decimals happens only when writing. Hit tolerance comes in image pixels from the canvas. Lines and unfilled outlines are hit near the stroke, so a click inside an empty rectangle reaches what is behind it; the last drawn item wins. A marquee selects what it intersects, as in Figma. Snapping prefers image and object edges and centres within a threshold (with guides), then the grid (without). Style presets 1 to 3 are built in with sizes only until SN-210 reads the `styles` file and the report palette.

## 2026-10-26 Undo keeps snapshots, not inverse operations

Refines the undo entry above. Each undo entry holds a label for the Edit menu and the sidecar, current step (by file) and selection before and after one command. Why: undo cannot drift from what a command did, no command carries undo code of its own, and the sidecar's arrays share storage between snapshots, so unlimited history in a session stays cheap. Annotation ids are inside the snapshots, so undo brings back the same objects and their selection. Rules out: per-command inverse operations, and `UndoManager` as the store (it is bridged to the Edit menu only).

## 2026-10-26 Editing history: what is one entry and what clears it

A reload from outside (checkout, another editor, an outside sidecar edit) clears undo and redo, since undoing would silently overwrite that work; the editor keeps the current step by file. A drag commits one `move` or `setShape` on mouse-up, live feedback being canvas-only state, so a drag is one entry. `editText` on one annotation updates the top entry until `end-text-edit` or any other command; each arrow-key nudge is its own entry. Selection and step moves are not entries; undo and redo restore the selection of that time and return to the step the change was on.

## 2026-10-26 Commands, the Dispatcher and the editor

`Command` is the vocabulary of every user action on a case and conforms to SCommon's `KeymapCommand`: keyable commands have kebab-case names for the keymap (`next`, `go-to N`, `nudge-left-10`, `preset N`, `undo`), the ones the canvas sends with geometry (`add`, `setShape`, `editText`, `move`, `select`, `toggleSelect`, `setCrop`) have none. `Dispatcher.apply(Invocation<Command>, to: inout EditorState) -> [Effect]` is pure as in sView, with vim counts; `CaseEditor` runs it on the main actor and hands sidecar changes to `CaseSession`. Rules applied: duplicate offsets copies by 10 image pixels, gives them new ids and selects them; `]` and `[` move the selection one place in drawing order; nudges are 1 or 10 image pixels, converted to stored pixels on scaled steps; `preset N` changes the selection, or the preset for new annotations when nothing is selected; a crop is clamped to the recorded size and refused when nothing of it is on the image; on a read-only case every edit, undo and redo is refused with a message while selection and step moves still work; the current step is an index into the steps whose image exists, navigation includes excluded steps, and a reload keeps the step by file.

## 2026-10-26 Built-in preset colours come from the report palette

Until SN-210 reads the `styles` file, preset 1 is primary blue `#00579C`, preset 2 danger red `#C62828` and preset 3 growth green `#00897B`, quoted from the palette of the Typst documents the reports go into, so screenshots match the decks and documents. Counters are filled in the preset colour with a white number; text is the preset colour, or white on a pill of it; soft fill is the colour at 15%; a highlight multiplies the colour at 25% into the capture like a marker; a spotlight dims everything outside its rectangle with black at 45%. Rules out: yellow (the palette has none) and amber (the palette reserves it for timeliness).

## 2026-10-26 Renderer order, numbering and scaling

Blur and pixelate are filtered from the bare capture and drawn before every other annotation, whatever their drawing order, because they hide things: nothing drawn is blurred by accident and a counter on a hidden hostname stays crisp; everything else draws in item order, so a spotlight dims what came before it. Counters are numbered in drawing order within a step, continuing across steps unless the root `counter` is `step` or the step has `restart_counter`; excluded steps and steps whose image is missing use no numbers, so an export reads without gaps. The crop is applied only by `Renderer.render` (export, clipboard); on screen the canvas draws the whole image and shows the crop itself. Style sizes are stored pixels and the annotation layer is scaled with the step, so a 2x step looks like its 1x original.

## 2026-10-26 Deterministic output and golden tests

Core Image runs its software renderer for blur and pixelate, and PNGs are written with fixed settings and no metadata, so the same input gives the same bytes on any Mac (a test renders twice and compares). Blur regions are clamped at their edges before filtering. Golden images live in `fixtures/golden/`, rendered at native size on a sample capture, and are compared with a tolerance (each channel within 3, at most 0.5% of pixels) so antialiasing changes between macOS versions do not fail the build; a failure leaves the render and a diff in `build/golden-diff/`. `make golden` rewrites them only when a rendering change is intended, and every changed golden is looked at before it is committed. Shape constants, inside `Geometry`'s bounds: arrow head 4 strokes long and 4 wide with the line ending at its base, corner radius one stroke, counter numbers bold at 1.1 times the radius, leaders at half the stroke width ending in a dot.

## 2026-10-26 Export paths, what is written and what is removed

Settles the open `assets/` export path from the case-document entry. Every step that is not excluded, annotated or not, is exported to `notated/<same relative path>` with a `.png` extension, so `assets/scap-...png` becomes `notated/assets/scap-...png` and a report can point at either folder by one prefix; two steps that would land on the same output are both skipped and reported, and a step whose image is missing is reported. A file is written only when its bytes would change, so a second export of an unchanged case touches no file and no modification time. A case export then removes the `.png` files directly in `notated/` and `notated/assets/` that it no longer produces and nothing else (other files, other sub-folders, anything outside). Exporting one step writes that file only, with the whole case's counter numbers, and the clipboard gets the same bytes. Rules out: flattening `assets/`, exporting only annotated steps, and cleaning anything but our own PNGs.

## 2026-10-26 Export refuses on an unreadable sidecar; the folder name cannot reach the originals

When the sidecar cannot be read, export is refused: from the folder alone it would replace annotated images with bare ones. Items it cannot draw and steps whose size is flagged (exported unscaled) are exported with warnings in the report. The export folder is `notated` until SN-403 reads it from the config, and any name that is empty, `.`, `..`, `assets` or contains a `/` is refused, so even a bad setting cannot write over a capture.

## 2026-10-26 Headless export lives in the app binary

`sNotate --export <case-folder>...` exports each case (or the case of an image path) without starting the app or opening a window, prints one line per file and a summary, keeps going after a refused case and exits 1 when any was refused, 2 when no folder was given. The logic is `HeadlessExport` in the core, so it is tested. Walking a whole PoC root and `make export ROOT=` remain SN-405 (Phase 4); the `snotate` launcher is SN-602 (Phase 2).

## 2026-10-26 The canvas: drawing, gestures and tools

`CanvasView` is a flipped `NSView` that draws in `draw(_:)` with Core Graphics through the export Renderer: the base (capture and redactions) is cached per step and rebuilt only when a blur region changes, the annotations are drawn every frame, so screen and PNG cannot drift. What a press, drag and release mean lives in the core as `Gesture` and is tested; the view converts points and draws its preview, and the release commits one Command. Tools are Commands (`tool select`, `tool arrow`) on `EditorState`; after drawing, the tool stays, as in Shottr, and the new annotation is selected; esc returns to selecting and, when already selecting, clears the selection; a drag under 4 image pixels is a click. Rules out: a CALayer per annotation, drag logic in the view, and tools as view state.

## 2026-10-26 Canvas defaults until zoom and config exist

The image is fitted to the window, centred, never above one image pixel per device pixel (zoom and pan keys are SN-502). Hit slop 4 view points, handle grab radius 8, snapping on within 6 view points to image and object edges and centres, grid off until the config file (cmd-; with it). Selection outline, 8-point handles, marquee and guides are drawn in view space at a fixed size in a muted amber accent, apart from the preset colours. The built-in keymap is in the core (`DefaultKeymap`); the user keymap file overlays it with SN-504. One case per window; closing saves a waiting change; without a case the window asks for one and cmd-o opens a folder or a capture.

## 2026-10-26 Scripted UI checks

`SNOTATE_WINDOW_SIZE`, `SNOTATE_KEYS` (keymap keys, `drag@x,y:x,y` and `click@x,y` in stored pixels) and `SNOTATE_SNAPSHOT=<png>` (the canvas drawn into a bitmap, then quit) let `make smoke` drive the real app without the Screen Recording permission, as sView's hooks do. Every canvas branch extends the smoke script with its tool and gates its merge on it.

## 2026-10-27 Rectangle and ellipse tools

`r` and `e` pick the tools; a second press while the tool is active switches the soft fill for the next shapes (E2's second-press variant), remembered per tool for the session and announced in a toast. `f` switches the fill of the selected rectangles and ellipses together as one undo entry, filling all if any is an outline and leaving other kinds alone. A shape is drawn corner to corner in either direction; shift makes a square or circle, option draws out from the centre, both combine; the dragged corner snaps unless shift is held; a side under 4 image pixels is a click. Handle drags take option to resize about the centre, shift still keeps a corner's aspect. After drawing the tool stays and the new shape is selected.

## 2026-10-27 A dragged point snaps to geometry, a moved shape to bounds

Refines the snapping rule. A single dragged point (an arrow end, a drawn corner, a handle) snaps to other annotations' geometry without stroke (`Geometry.outline`: a rectangle's rectangle, an arrow's points), so a corner drawn onto another rectangle's corner meets it exactly; a moved selection snaps by its bounds, outer stroke edge to outer stroke edge. Why: the shapes smoke test drew a rectangle that snapped two pixels short of its neighbour because point snapping used stroke-inclusive bounds.

## 2026-10-27 Counter tool

`n` picks the counter tool: a press shows a counter that follows the pointer and lands where it is released, so a click places it there; its centre snaps to geometry unless shift is held; pressing on an existing counter places a new one; the tool stays and the new counter is selected. Counters have no size to drag (the preset sets it) and no fill-style variant, so a second `n` does nothing; the per-step restart SN-203 asks for is `N`, the `restart-counter` command, announced in a toast. The canvas numbers counters with the step as drawn, preview included (`EditorState.counterNumbers(items:)`), so a held counter shows its number and the ones after it, here and on later steps, show theirs.

## 2026-10-27 Text tool and in-place editing

`t` picks the text tool; a click starts text with its top-left corner there, a drag starts it where released with a leader back to the press point (whether it was a drag is the pointer's distance, not the snapped end's), and the position snaps unless shift is held. A second `t` switches the pill for new texts, and `f` switches it on selected text, the text counterpart of a shape's fill. Editing opens with a double-click (select tool) or enter on one selected text (the `edit` command, whose `beginTextEdit` effect asks the canvas to open the field). Enter commits, shift-enter breaks the line, esc, a click elsewhere, undo and closing the window commit too; undo while typing commits then undoes, so on new text it cancels. A new text exists only in `TextEdit` until committed as one `add`, and an empty one leaves nothing; existing text is edited live as one coalesced Edit Text entry, and emptied text is deleted.

The field is a transparent `NSTextView` that only shows the caret and selection; the export renderer draws the glyphs, pill and leader, so what is typed is what is exported. It lives in a layer whose coordinates are the step's stored pixels and uses the renderer's font size and line height: a field set at the zoomed point size picked another optical size of the system font, ran wider than the glyphs and put the caret past the text. Its own undo is off so the case has one history. Rules out: an opaque field swapped for the rendered text on commit.

## 2026-10-27 Edits are kept at the sidecar's precision

Every edit is rounded to two decimals where the Dispatcher applies it, exactly as `SidecarWriter` writes, so the document in memory equals what reading our own save back gives. Why: mouse positions are fractional, and without this every autosave looked like an outside change to the folder watch, which reloaded and wiped the selection and undo about half a second after most edits made with a real mouse. Also: a press is a click or a drag by the pointer's own distance, never the snapped end's, since snapping can jump further than the click threshold.

## 2026-10-27 Highlight tool; f switches the selected shape's variant

`h` picks the highlight tool, drawn like a rectangle (corner to corner, shift square, option from the centre, snapped corner, click threshold); a second `h` switches the next highlights between marker and spotlight with a toast. `f` now means the selected shape's variant in every tool: the soft fill of rectangles and ellipses, the pill of text, the spotlight of a highlight; across a mixed selection it turns every variant on if any is off. A spotlight is hit inside its rectangle only, so clicks in the dimmed area reach what is drawn there.

## 2026-10-27 All spotlights of a step are one dimming

The renderer draws one black 45% dimming per step, where the first spotlight sits in drawing order, as the image minus the union of every spotlight's rectangle (CGPath boolean operations, so overlapping holes stay bright, which an even-odd fill would not). Why: "look here and here" is common on console screens, and a second spotlight used to darken the first one's area. Annotations drawn before the first spotlight are dimmed with the image; those after it are not.

## 2026-10-27 Shift is a letter's case in key bindings, and scripted keys say so

The shared key grammar carries shift in a character's case (`G`, `cmd-Z`) and keeps `shift-` for named keys (`shift-left`); `Key` drops the shift flag from single characters. So `cmd-shift-z` is cmd-z, and the default keymap had silently bound cmd-z to redo. Redo is `cmd-Z`, a test fails when two default lines parse to the same keys, and scripted key events keep shift in the character's case, as a keyboard does.

## 2026-10-27 Blur tool and redaction strength

`b` picks the blur tool, drawn like a rectangle; a second `b` switches the next regions between blur and pixelate, `f` switches selected ones, and a click anywhere inside a region selects it. The tools with a variant are an explicit list (rectangle, ellipse, text, highlight, blur). Redaction strength is the larger of the preset's radius and a share of the region's shorter side, a quarter for pixelate blocks and a fifth for the blur's sigma, so console-size fields keep the preset radius and large labels become unreadable; Core Image's pixellate samples one pixel per block rather than averaging, which hides more. While a region is drawn, moved or resized it shows as a frosted, dashed outline, and the cached base, built from saved items only, is blurred on release. What a region changes: only the export in `notated/` and the clipboard; the capture is never written and the sidecar holds the rectangle, not what was under it. Blur and pixelation of known fonts can sometimes be partly reversed, so a solid "redact" variant for real secrets is logged as P2 under SN-206.

## 2026-10-27 A click never moves or reshapes

A move or handle drag commits only when the pointer itself travelled the click threshold (4 image pixels), the rule drawing tools and text leaders already follow; snapping alone used to move a shape that was only clicked to select it. Adjustments smaller than the threshold are what the 1-pixel nudge keys are for.

## 2026-10-27 Crop tool

`c` picks the crop tool, which has no variant. The crop is one rectangle per step, so its gestures commit `setCrop` (clamped to the image, one undo entry): a press outside the crop draws a new one, inside moves it, its eight handles resize it; shift locks a new crop to the image's aspect and keeps a resized one's aspect, option works from the centre, the dragged edge snaps unless shift is held, and a click changes nothing. `C` (`crop-previous`) copies the nearest earlier step's crop, since captures share a geometry, and says so when there is none; with the crop tool active, delete and backspace remove the step's crop instead of the selected annotations. The canvas keeps the whole capture and shows the crop: darkened outside (60%) with border and handles while cropping, dimmed lightly (35%) with a faint border otherwise; annotations outside it are allowed and export clips them.

## 2026-10-27 Key conflicts settled: brackets, digits, pan, space

`[` and `]` are the sibling case (SN-501), as in sView, and z-order moves to `cmd-[` and `cmd-]`, as in Figma. Why: moving from case to case is the frequent move when reviewing a PoC and the two apps should agree on keys they share; z-order is rare and done with the mouse in hand. Digits `1` to `9` stay presets and the default keymap has no count prefixes: presets are pressed constantly while annotating, cases have 6 to 15 steps, and `:N`, `gg` and `G` cover jumps; the shared matcher gives bindings priority, so a user keymap (SN-504) that unbinds the digits gets counts back. Arrow keys pan when nothing is selected and the image overflows, and nudge the selection otherwise, so `h` stays the highlight tool; this is sView's rule (pan when it overflows, else navigate) with the selection in place of navigation, and it pans vertically, which `h`/`l` could not since `j`/`k` are steps. `space` only pans while held, as in drawing tools; it is not next step, so an abandoned pan never changes step. Rules out: counts by default, context-dependent digits, `h`/`l` pan, tap-space as next step.

## 2026-10-27 Zoom and pan

A core `Viewport` holds the zoom and the centre and gives the canvas its `ViewTransform`; zoom commands only return effects, so zoom is view state, never in the sidecar or the undo. The unit is sView's, device pixels per image pixel: fit is never above 1, `0` is 1:1 on the screen, keys step by 1.25 between the smaller of fit and 0.1 and 16. Zoom and centre are kept across steps in stored pixels, so a re-shot 2x step shows the same region; resizing the window re-fits only at fit. Keys zoom about the view's centre (`+`, `-`, `=` fit, `0` actual, and `cmd-=`, `cmd--`, `cmd-0`, `cmd-9` in the View menu, as in Preview); pinch and cmd-scroll zoom about the pointer; two-finger scroll pans. Arrow keys with nothing selected pan an eighth of the view, shifted 90%, only along an axis that overflows. `z` arms one drag that zooms to its area whatever the tool (a click zooms in one step there; `esc` or any command disarms it). Holding `space` pans with any drag; it is handled by the canvas, not the keymap, since the grammar has presses and not holds. Above two device pixels per image pixel the capture is drawn without smoothing, so its pixels show for exact placement; handles, outlines and guides keep their size on screen. A toast shows the zoom as a percentage of actual size. Also: scripted runs send a menu key's action to the first responder, because their window is never key and the menu otherwise swallowed the key.

## 2026-10-27 Sibling cases and the command line

`]` and `[` (`case-next`, `case-previous`) open the sibling case in the same window, as sView does, after saving the case being left. When the open folder has a case name, only case-named siblings count, so product folders, `golden/` or a stray folder of PNGs are skipped; elsewhere any folder with images counts. Folders without captures, directly or in `assets/`, are skipped, in natural order, and an empty open case still has neighbours. The tool and its variants, the preset for new annotations and the zoom stay with the window, since cases share a capture geometry; selection and undo stay with their case. A case already open in another window comes to the front instead, because two editors on one sidecar would overwrite each other's autosaves. The sibling opens on its first step; past the first or last case, or when it cannot be opened, a toast says so and the window stays. The names say case rather than sView's folder because a case is what moves; the keys are the same. `:` opens a one-line prompt: a number goes to that step (`:5`), anything else runs as a keymap command (`:zoom-fit`), and a mistake is a toast. The prompt view is adapted from sView's into the app, without completion, since the shared layer is core only; it is the first UI both apps carry and a candidate for scommon. No Go menu yet: bare-key menu equivalents are unusual on macOS and the full menus are SN-505.

## 2026-10-27 Config and keymap files

`~/.config/snotate/` (or `$XDG_CONFIG_HOME/snotate/`) holds `config` and `keymap`, written with the defaults on first run and never over the user's files. The keymap file is laid over the built-in bindings, as in sView: a line binds or rebinds and `<keys> nop` unbinds, so `1 nop` to `9 nop` gives count prefixes back. The config accepts only keys with something behind them: `notated_dir` (the export folder, one plain name other than `assets`, checked by the same rule export uses) and `snap`; `export_scale`, `counter` and `grid` arrive with their features. Unknown keys and bad values are issues that keep the default, so the app always starts; the first one is a toast with how many more there are, on launch and after a reload that brings one. Edits apply at once to every window, through a watch on the folder and a check when the app becomes active; a key sequence typed halfway is dropped. Headless `--export` reads the config too, printing its problems as warnings that do not change the exit status. `:set <key> <value>` checks the value, rewrites only that line of `config` and applies it; `:map` is left out, editing the keymap file is the way. `:export-config [path]` and File > Export Config to Desktop zip `config`, `keymap` and `styles` (when present), never `state.json`, as one `snotate/` folder; `ConfigExport` is adapted from sView's into the core, like the prompt view a candidate for scommon. Parsing, loading and export are in the core and tested; the app owns only the watcher, the per-window matchers and the toast. `make smoke` sets `XDG_CONFIG_HOME` to `build/smoke/config` so a user's keymap never changes what it presses.

## 2026-10-27 Style presets from the styles file

`~/.config/snotate/styles` holds blocks that start with `preset N` (1 to 9, the keys that pick them), each line under it one `key value`: `color #rrggbb`, `stroke`, `font` (size), `counter` (the circle's diameter) and `blur`, sizes in image pixels. No alpha: the tints come from the renderer. The family stays the system font, which covers Vietnamese; a family can be added later as `font <size> <family>` without breaking files. A block starts from the built-in preset with its number, or built-in preset 1, so it names only what differs; the file adds and overrides presets and never removes one, since sidecars may name it. Bad lines are issues that keep the value, a block whose `preset` line is bad is skipped, and they are reported with the config's. The file is written on first run as the built-in presets, a test checks it parses to exactly `Styles.builtIn`, and tests and goldens pass the built-in presets explicitly, so they never depend on the machine. A preset key the styles lack is refused with a toast; a sidecar that names one still renders as preset 1. Edits apply at once to every window, undo kept, and the canvas keys its blurred base on the styles. Whose styles: the machine's. The sidecar keeps preset numbers only, so a case re-exported with other styles comes out in other colours and `notated/` changes; a team shares a look through `:export-config`. Rules out, for now: styles written into each sidecar, which would contradict one fact per key and copy the palette into every case.

## 2026-10-27 Storyboard and captions in the memo

`cmd-2` shows the storyboard, every step as a frame in reading order with its number, file name and caption, and `cmd-1` the single step; the selected frame is the current step. In the storyboard enter opens the step, arrows move between frames (up and down by row), `+` and `-` size the frames, `i` or a double-click on a caption edits it, and tool keys do nothing, since drawing happens in the single view; step commands such as `C` and `N` still act on the selected frame. `i` in the single view goes to the storyboard and edits that step's caption. Esc in a step opened from the storyboard drops the tool, then the selection, then goes back. A frame is the step as it will be exported (crop, redactions, annotations, case numbering), rendered off the main thread and cached by what it depends on; an excluded step is dimmed and labelled. The grid paints at once with placeholders, which is how the 500 ms target is read: a 30-step case paints in about 10 ms and its visible frames have pictures in under 100 ms. The view is AppKit, so keys go through the same keymap and test hooks as the canvas. A caption is the memo bullet when the memo references the image, the sidecar's `caption` otherwise; an unreadable memo makes captions read-only. A memo caption edit rewrites that one line and is written at once, only if the file still holds the bytes last read; otherwise the case reloads from disk and the edit is dropped with a toast. The written memo becomes the one the folder watch compares with, so our own write never reloads. An empty caption writes the placeholder `description` back. The undo snapshot carries the memo, so cmd-z undoes a caption wherever it lives. Captions in the sidecar move into the memo when it references their image and has no caption of its own (no bullet or the placeholder), on open and on reload, outside undo; where the memo already has other text the memo wins and the sidecar caption is kept and reported, so nothing is lost. Markdown in a caption shows as typed. Rules out: SwiftUI's grid with a second focus model, captions outside undo, debounced memo writes.

## 2026-10-27 Exclude and stamp across steps

`x` toggles a step's `excluded`, with a toast saying which way; nothing is deleted, export skips the step and counter numbering leaves it out. The author deletes excluded captures before the rename script runs, so `:excluded` toasts their names and puts them on the clipboard one per line, and headless export prints an `excluded <file>` line for each; sNotate never deletes a capture. Stamping (SN-306) copies the selected blur and highlight regions, or the crop while the crop tool is active, onto other steps: `>` onto every later step (`stamp-following`), `<` onto the previous one, and `:stamp-next` and `:stamp-all` through the command line. Counters, arrows, shapes and text are never stamped, since a counter would renumber the story and the others are rarely right on another step. Excluded steps and steps recorded at another size are skipped, since stored pixels line up only between captures of one size (a 2x re-shot step records the 1x size and is included); a region a step already has (same shape, variant and preset) is not added again, and a stamped crop replaces the step's crop. One stamp is one undo entry for every step it touched, and the copies are independent items with their own ids. Rules out: stamping counters or arbitrary shapes, linked copies, and deleting files from sNotate.

## 2026-10-27 Reorder and the rename plan

Story order is the sidecar's order: `J` and `K` move the current step later or earlier and a drag in the storyboard drops a frame into the gap an amber bar shows, each one undo entry; counters renumber at once. The file names follow only through `:rename-plan`, a sheet listing every rename, what is left alone and why, and what blocks it, whose button is the only way captures are renamed (a CLAUDE.md rule now: originals are renamed only by a confirmed plan, never rewritten). The storyboard says when story order differs from the names. The plan follows the evidence procedure's rename step so an evidence script finds nothing left to do: captures directly in the case folder, `.png`, `.jpg` or `.jpeg`, `<case-id>-<nn>` with two digits widened at 100, extension lower-cased. Before a memo exists every such capture is numbered from 00 in story order, numbered ones included, since nothing references them yet; once a memo exists, numbered captures keep their numbers, as the procedure says, others take numbers after the highest, a capture the memo references is never renamed, and captures whose numbers then disagree with story order are listed for the author to fix in the memo by hand. Excluded steps (delete them first), `assets/` and other image types are left alone and listed; a target name held by a capture outside the plan blocks it, as does an unreadable sidecar or memo. Applying moves every source to a temporary name first so swaps never collide, never overwrites a file outside the plan, puts back what moved if a rename fails, moves the sidecar keys with the files, rebuilds the editor (outside undo, history cleared, since it names the old files) and drops the cached pictures, since a name can now hold other bytes. Found while building it: a reload from disk rebuilt the editor with the default view and tool, so an outside edit or a rename threw the window out of the storyboard; the view, tool and its variants now carry over like the preset. Rules out: moving memo blocks, renaming without the sheet, renumbering captures a memo references.

Image files dragged from Finder or sView onto the storyboard land in the gap an amber bar shows, and `cmd-v` there inserts the clipboard's images (files or image data) after the selected frame, through the Edit menu's Paste. ## 2026-10-27 Export options in the config

## 2026-10-27 Export a PoC root

`sNotate --export <path>` and `make export ROOT=<path>` take a case or a PoC root (SN-405). A folder with its own sidecar or captures (directly or in `assets/`) is a case; any other folder is a root, walked recursively in natural order without looking into case folders and skipping hidden folders, the export folder and `assets/`. Every case with a sidecar is exported with the config's folder, options and styles, each as its own report block; cases without a sidecar are counted as skipped, not exported, since bare copies of every capture would only be noise; a last line totals the tree. ## 2026-10-27 AppKit work never runs inside a task job

In the app target, Swift tasks only wait or compute; anything that touches AppKit runs from a main-queue block through `MainQueue.async` or `MainQueue.after` (the key timeout, the toast fade, thumbnail, export and config export completions, the test hook). Why: the two activation crashes were an Objective-C exception thrown inside a main-actor task job. The Swift runtime swallowed it, but the unwinding skipped the job's executor bookkeeping, and the next main-actor check, on `applicationDidBecomeActive`, trapped minutes later with a backtrace that pointed nowhere near the cause; a scratch app reproduces it frame for frame. In a main-queue block the same exception ends the app at once with its reason and the throwing frame, and exceptions during real event handling are still caught by AppKit as before. `make activate` checks both. Scripted runs also ignore saved window state, so the reopen-windows alert after a crash cannot stall smoke. Rules out: `Task { @MainActor in ... }` or `MainActor.run` bodies that call AppKit, and making delegate methods `nonisolated` to skip the check.

## 2026-10-27 What the window says when the disk changes under it

## 2026-10-27 The capture is a layer under the canvas

SN-606. The canvas no longer draws the capture: a `CaptureView` just below it shows the step's base (capture and redactions, from `Renderer.base`) as the contents of a layer the GPU scales, and the canvas draws every annotation and overlay over it with the one renderer. Below full size the layer gets `Renderer.displayCopy`, the base halved to the smallest power of two that still covers every device pixel, in 32-bit BGRA; at full size the base itself. Why: AppKit records the canvas drawing and replays it on the main thread in the commit, through a half-float pass; replaying the capture cost 5 ms of an 8.3 ms frame at 1600x1000 and up to 72 ms on the first gesture at 8k. Neither an 8-bit layer store nor a window depth limit changed that pass. Export, golden images and snapshots are unchanged: the pixels on screen are the same base, scaled by the GPU instead of Core Graphics, and `CaptureView` draws itself for snapshots. Cost: at full size Core Animation keeps its own copy, 256 MB for an 8k capture. Rules out: drawing the capture in `draw(_:)`, tuning the backing store format.

## 2026-10-29 Remove a step (supersedes "sNotate never deletes a capture" in "Exclude and stamp across steps")

Putting back moves the capture back from the Trash (or leaves it where Finder's Put Back already took it), inserts the entry after the one it followed, and restores the memo only when it still holds the bytes the removal wrote; a memo changed since is never overwritten and the toast says the block was not put back. Order on removal: the Trash first, then the memo, which puts the capture back if it cannot be written, then the sidecar. Refused while the sidecar or an existing memo cannot be read. Removals are not redone and are forgotten when the window leaves the case; Finder's Put Back still works. Smoke uses `SNOTATE_TRASH`, a folder of its own.
